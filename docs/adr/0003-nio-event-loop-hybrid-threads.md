# 网络层改为手写 NIO 事件循环（Kafka 路线）+ 混合线程拓扑

---
status: accepted
supersedes: ADR-0001 的 Socket I/O 部分（虚拟线程保留给磁盘与校验等阻塞操作）
---

实测（docs/PERFORMANCE.md）：阻塞 Socket + 虚拟线程在回环下单 Peer 35MB/s，每 16KiB 块
~450µs 固定成本（双方 park/唤醒 + 每帧系统调用），4 Peer 聚合仅 +11%。库定位为通用第三方库
且明确追求尽可能高的性能与并发；零传递依赖为硬约束，故排除 Netty（4MB+ 传递依赖、
版本/CVE 管理税）。参照 Kafka 的先例（自研 NIO Selector 事件循环达到世界级性能、零依赖），
决定自研事件循环承载 Peer 连接 I/O。

## 决策

- **拓扑（混合）**：1 个 Selector 线程管理全部 Peer 连接（epoll 循环、合帧解码、批量写、
  写背压），磁盘写与 SHA-1 校验留在虚拟线程池——事件循环零阻塞、虚拟线程零 Socket I/O，
  两种模型各司其职。
- **缓冲策略**：16KiB 块缓冲池化 + 直接 ByteBuffer 复用（Kafka 招数中对本协议收益最大的一项）。
- **迁移路径（C1→C5）**：`PeerTransport` 接口隔离 → `NioTransport` 实现 → 引擎迁移
  （含异步 Piece 校验、存储写通道分片、调度器锁拆分）→ 差分验收 → 回到收尾任务。
  现有阻塞实现保留为 `BlockingTransport` 参照实现，全部 tools 验收对两种实现参数化对拍；
  迁移完成后降级为内部调试工具（不对用户暴露、不做双实现承诺）。

## 内部验收红线（不对外承诺，达不到才重议 Netty）

单 Peer 回环 ≥ 500MB/s；8 Peer 聚合 ≥ 1GB/s；万级连接可运行。

**红线判定结果（2026-09-15，C4 收官）**：单 Peer 110MB/s、8 Peer 聚合 ~98MB/s，均未达。
但归因结论是**换 Netty 也无济于事**：聚合天花板来自"每块工作内联在唯一选择器线程 +
调度/ choking/ 位图三把锁的串行链"，事件循环框架同样要求把这类工作卸载到 worker 池——
这是引擎线程模型问题，与传输实现正交。下一层杠杆见 docs/PERFORMANCE.md；真实网络场景
（带宽 ≤1Gbps）已无差别，C 线在此收官，剩余优化转入按需任务。

## Considered Options

- **Netty**：微基准最强，但违反零依赖硬约束——否决。
- **优化现状（批帧 + 异步校验 + 锁拆分）**：预计单 Peer 100–300MB/s，与事件驱动仍有 2–3×
  结构性差距（每批一次 park/unpark 无法消除）；用户明确要"尽可能优化性能"——不足。
- **纯事件循环做所有事（Kafka 原样）**：磁盘写与 SHA-1 是阻塞操作，放进事件循环会卡住
  全部连接——改为混合拓扑。

## Consequences

- 状态机复杂度上升（半包、OP_WRITE 注册竞态、慢消费者背压、无阻塞读下的超时管理），
  靠差分验收的故障二分能力消化。
- 可读性相对阻塞模型下降——以 BlockingTransport 保留为"可执行规格"补偿。
- 连接预算提升至万级（单 epoll 循环舒适区），README 将明确 ≤10k 为设计量级。
